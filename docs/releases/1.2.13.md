# PremiereCalendar 1.2.13 — shared database item cache

Reusable title metadata and external scores now live in a normalized application-database cache shared across weeks and filters. Records remain for three calendar months since last use. Batch reads, reservations and writes reduce database round trips; concurrent requests share enrichment work. Existing verified week files seed the cache without provider calls and retain their original success timestamps.

Retention and freshness are separate. Metadata has a seven-day fallback refresh and scores a 24-hour refresh, with earlier targeted metadata invalidation from successful TMDb and TVmaze change checks. Only known cached TMDb IDs returned by the change lists need individual change-history lookups. Score-only refreshes avoid metadata and artwork calls. TMDb season-one, external-ID and title-resolution responses also survive restart; positive resolutions remain fresh for 90 days and negative results for six hours.

Failed provider refreshes retain good values and their original clocks. Generation and metadata-revision checks protect against stale concurrent writes; week publication and completed-cache reads reconcile shared item versions. Calendar discovery continues to determine membership, release dates and first-series debuts. English/Dutch defaults, runtime filters, disk image storage and the 02:00 Brussels current/next-month warmup remain in place. Detailed cache/provider/job timings are logged automatically.

This release adds schema 4 without changing existing tables or migrations 1–3. An old schema-3-only image cannot directly roll back against schema 4. The operational fallback is the schema-4-capable release with `ItemEnrichmentCache__Enabled=false`; a database restore requires a separate deliberate recovery decision. Preserve the pre-upgrade backup and application data. See [cache configuration and operations](../ItemEnrichmentCache.md).

Local source validation passed 1,229 tests: 650 unit, 191 component and 388 integration tests, including actual PostgreSQL, plus one expected Linux-only skip. Independent Astra High review has no open P0–P2 findings. Coverage includes three-month cleanup, restart/cross-week reuse, score-only refreshes, optional failures and cooldowns, changed dates, generation/revision races, per-ID batch invalidation, and preservation of manual repairs. The first integration run identified an outdated retention fixture and loss of partial Watchmode regional data; both are corrected. A readiness test returned 503 on that run, then passed in isolation and in the complete rerun; no production readiness failure is inferred from it.

An initial image candidate from `f91759596bc77260b70e6d138c2e8a663c67eab9` passed its security/runtime/migration gates but was withheld before activation. A final three-session review found that a foreign vote-only revision could replace newer discovery fields in an existing week. The corrected reconciliation preserves those fields when the metadata-success clock is unchanged, while applying accepted IDs, availability and votes. The candidate archive and evidence remain preserved locally; the corrected source is rebuilt and gated separately.

Image security, backup migration and installed acceptance are recorded below. Hosted GitHub CI remains disabled; release builds, tests, scans and publication run locally.
