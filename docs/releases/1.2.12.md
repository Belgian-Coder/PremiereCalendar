# PremiereCalendar 1.2.12 — nightly month caches

The app schedules current- and next-month cache preparation at 02:00 Europe/Brussels. It creates independent durable week jobs for the default English/Dutch Series and Movies profiles, with first-debut series and the 45-minute movie minimum. Full weeks at month boundaries are included, current-week work comes first, and both profiles are interleaved. Explicit user filters remain unchanged.

Nightly work rebuilds calendar snapshots using normal provider cache lifetimes and cached enrichment. It does not force every external service call. Calendar cache freshness defaults to 30 hours so overnight results remain useful through the day; explicit configuration overrides remain respected. Jobs survive restart, yield to foreground work and retain bounded retries. Cache coverage is verified independently of enqueue success. Operational and performance logs retain outcomes, row counts, job IDs and measured durations.

This release does not establish a cold-provider speedup. Before the change, the installed 31-row current-series cache visit took 828 ms from browser reload to the matching completed DOM. The correlated server page event took 8.99 ms and recorded direct complete-cache reuse with zero provider events or attached jobs. These are separate measurement boundaries, not production percentiles. Explicit provider refreshes on v1.2.11 took 11.776–48.888 seconds with retained provider caches; wider historical workloads took minutes.

The application delta passed 1,134 local tests: 613 unit,191 component and330 actual-PostgreSQL integration, with one expected Linux platform skip. Independent Astra High review has no open findings. The first image candidate was rejected before activation because the Alpine runtime lacked timezone data. The corrected Dockerfile copies full timezone data from the digest-pinned SDK, preserving configurable IANA zones without a new package-download dependency. Exact-image security/runtime gates and installed acceptance remain pending. Hosted GitHub CI remains disabled. PostgreSQL, application data and the backup container are preserved; no database migration is required.
