# v1.2.22 - Steadier calendar autoload and provider cache

## Changes

- The calendar day list keeps loading while its "show more" sentinel stays in
  view. Before, a load that ran while an earlier window move was still pending
  (or a load that did not trim cards) left the sentinel visible without a new
  visibility event, so autoload stopped after one batch and a first visit to a
  busy day (for example `/series`) could take several seconds longer. Forward
  autoload now resumes when the day window settles and the sentinel is still
  near the viewport; it never reverses direction on its own.
- The provider response cache no longer counts a save that finished
  successfully, but after its time budget, as a storage failure. Such late
  saves could open the five-second storage backoff on a busy host. Saves that
  fail or are cancelled by the budget still count.

## Local build, test and release harness

- Release gates have a per-step deadline. A hung step is stopped, recorded as
  failed (exit 124) with its resource prefix and a cleanup hint, and no later
  step starts.
- Release smoke and restore-check networks retry with another explicit subnet
  when the derived one overlaps an existing network.
- The release bundle no longer copies the test hosts' runtime logs
  (`local-data`); they stay in the checkout's `artifacts`.
- A failing age check of the cached Trivy database discards the copy instead
  of treating it as fresh; the 6-hour freshness gate is unchanged.
- The WSL test result cache keys on the resolved thread budget, and explicit
  test timeouts from 60 s work again (the cleanup grace scales below 900 s).
- The HarnessProcess static check absorbs a cold interpreter start before its
  timing assertions (an intermittent first-run failure on macOS).

## Release boundary

The database schema stays at version 4, so an app-only rollback to 1.2.21 is
possible. Installed acceptance is recorded after the exact release passes its
gates and is verified on the NAS.
